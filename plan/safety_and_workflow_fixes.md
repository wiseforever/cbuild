# 清理安全与构建工作流缺陷修复

状态：已完成（当前修复范围）。原七项修复及复审追加的 Windows PATH 限定已实现并通过自动化验证；用户决定本轮不增加全局安装并发互斥，仅保留已知限制说明，不作为待实施任务。真实 Windows/macOS 环境和 VS Code 界面交互未实测。

## 问题表与解决方案

本表保留本轮列举的全部七项问题及对应方案，修复后不删除。最初检查中，第 1～6 项已在 Linux 临时项目中复现，第 7 项由静态代码检查发现。

| 编号 | 问题 | 触发条件与影响 | 涉及文件 | 解决方案 |
| --- | --- | --- | --- | --- |
| 1 | 清理命令缺少误删保护 | `output_dir = .` 且 `use_output_auto_subdir = false` 时，`-c` 会删除源码目录；配置为源码祖先目录也有风险。默认配置不触发。 | `cb.py`、`cb.sh` | 删除前解析源码与构建目录的真实路径，拒绝删除源码目录及其祖先目录，包括符号链接别名；允许清理正常构建目录。 |
| 2 | 全局更新失败丢失旧脚本 | 安装器先删除旧版本再下载；必需脚本下载失败后，原来可用的入口也被删除。 | `install.sh` | 在安装目录内暂存下载，必需脚本全部下载并准备成功后再替换；成功后才删除另一变体；退出时清理暂存目录。可选卸载脚本下载失败保留旧副本。 |
| 3 | Ninja 下纯 C 项目无法识别可执行文件 | 只识别 `CXX_EXECUTABLE_LINKER__`，不识别 `C_EXECUTABLE_LINKER__`；编译成功后 `-b` 报失败，`-r` 无法运行。 | `cb.py`、`cb.sh` | 路径解析和可执行文件列表同时匹配 C/C++ 链接规则；验证默认程序与指定程序的运行。 |
| 4 | 自定义 target 成功后仍可能报失败 | `-b --target deploy` 等目标成功执行后，仍强制查找可执行文件；无可执行文件或程序尚未构建时返回失败。 | `cb.py`、`cb.sh` | 以 CMake 构建退出状态判断成功；可执行文件日志及 VS Code 启动路径更新改为可选步骤；`-r` 仍严格检查程序，真实构建失败仍返回非零。 |
| 5 | Bash 可执行文件列表漏列 Ninja 程序 | `--list-execs` 的二次正则判断未匹配冒号后的空格，已有 C++ 程序仍提示找不到。 | `cb.sh` | 统一筛选与判断规则，匹配冒号后的空白及 C/C++ 链接规则；与 Python 版结果对照。 |
| 6 | 构建类型变化后目录缓存未失效 | 存在相关 VS Code 配置时，`-t Debug -g Release` 会提前缓存 Debug 目录，随后在其中写入 Release 配置。 | `cb.py`、`cb.sh` | 为构建目录缓存记录对应构建类型；类型变化时重新计算目录，不改变 `-t` 持久修改与动作参数临时覆盖的语义。 |
| 7 | 插件初始化与安装器默认行为不一致 | 选择 Python 却未传 `--python`，实际默认安装 Bash；初始化默认全局安装，但插件按钮只查找项目根目录脚本。 | `tools/cbuild-plugin-vscode/src/extension.ts` | 统一为全局安装和全局脚本查找；内置源显式使用 `--global --python` / `--global --bash` 及相同目录的 `--prefix`，运行时先查 PATH 的 Bash/Python，再查备用目录（默认 `~/.cbuild`）的 Bash/Python；通过独立 `--vscode` / `--config` 命令配置项目，安装器也先查 PATH，自定义源命令保持原样。 |

## 复审追加问题

| 编号 | 问题与影响 | 方案及当前状态 |
| --- | --- | --- |
| R1 | Windows 的裸 `where cb.sh` 默认还搜索当前工作目录，可能把不在 PATH 的项目脚本或安装器当作全局版本。 | **已修复。** 脚本发现使用 `where $PATH:<文件名>` 限定 PATH；模拟 `where` 的 cwd 优先行为，覆盖构建脚本、安装器、目录兜底和用户显式将项目放入 PATH 的情况。新增 10 项回归，插件共 51 项通过；真实 Windows 仍需实测。 |
| R2 | 同一安装目录并发安装 Bash/Python 时，两个过程可能在各自发布后删除对方变体，均报告成功但最终两个入口都不存在。 | **已知限制，本轮暂不修复。** 临时目录中已通过交错执行复现；用户评估后决定先不增加互斥保护，仅文档说明，不作为未完成任务。 |

### R2 已知限制：不要对同一目录并发安装或更新

- 当前安装器没有互斥保护；尤其不要同时向同一个安装目录安装 Bash 和 Python 两种变体，即使两个进程都报告成功，也可能互相删除脚本。
- 从多个终端或多个 VS Code 窗口操作时，应等待前一次安装/更新结束，再启动下一次；不同安装目录不受这一互相删除问题影响。
- 如果已经发生，应等待所有安装进程结束，再向原目录单独重装所需变体，恢复缺失的入口。
- 曾评估过“原子 `mkdir` 锁、仅串行化发布阶段”的方案；用户决定本轮先不加入。当前没有锁目录、等待或自动抢锁机制。

## 后续方案调整

第 7 项最初采用显式 `--simple --python` / `--simple --bash`，让初始化与当时的项目脚本查找方式一致。用户随后明确要求切换为全局脚本、Bash 优先、全局初始化，并增加 `--vscode` / `--config`。用户进一步澄清脚本应优先从环境 PATH 发现，没有才退回默认 `~/.cbuild` 或配置的备用目录，安装器同步遵循此顺序。当前代码及上表已按新要求更新，原始问题表继续保留；详细方案见[插件规划](vscode_cbuild_tools.md)。

## 兼容性与风险

- 不改变安装器默认全局 Bash 模式；插件先从扩展宿主 PATH 发现脚本，再查 `cbuild.installDirectory` 备用目录，并使用解析后的路径。没有额外的项目目录回退；用户显式放到 PATH 的项目脚本仍会被发现。内置安装命令仍以配置目录为 `--prefix` 目标，不自动推断 PATH 脚本所在目录作为更新目标。
- 不扩大多动作命令语义；保留 `-t` 持久写配置、动作参数临时覆盖类型的行为。
- 测试只在一次性临时目录执行清理与安装，不触及真实项目或用户安装。
- 实际 Windows/macOS 环境需要后续验证；本轮以 Linux 实测为主。
